# LLM 推理服务部署 — 阶段一 & 阶段二 实验报告

## 一、实验概述

本报告覆盖项目前两个阶段的完整实验数据与结论：

- **阶段一**：搭建可复现的异步压测体系，建立基线性能数据（并发 1~64）。
- **阶段二**：扫描吞吐与延迟的 trade-off 曲线，对比 `--max-num-seqs` 等关键参数对 batching 效率的影响，定位最优工作点。

**核心结论**：在 P99 < 15s 的延迟约束下，最优工作点为并发 64，墙钟吞吐约 2200 t/s，相比单请求提升约 **36 倍**。`--max-num-seqs` 在不过载时几乎不影响性能，其核心价值是**过载保护**——当客户端并发超过 64 时，限制 64 会将吞吐硬锁死在 ~2250 t/s，防止无限排队导致雪崩。

## 三、压测工具说明

自研异步压测脚本 `bench_compare.py`（约 120 行），核心能力：

1. **并发控制**：`asyncio.Semaphore` 精确控制客户端并发数。
2. **流式 TTFT/TPOT 分离**：通过 `stream=true` 读取 SSE 流，记录：
   - **TTFT**（Time To First Token）：请求发送到首 token 到达的间隔，反映 prefill 阶段效率。
   - **TPOT**（Time Per Output Token）：首 token 后到流结束的平均每 token 间隔，反映 decode 阶段效率。
3. **墙钟总吞吐**：`total_completion_tokens / wall_time`，衡量 GPU 在真实时间内的总产出能力。
4. **统计指标**：P50 / P99 端到端延迟、P50 / P99 TTFT、P50 / P99 TPOT。

## 五、阶段二：Batching 优化与 Trade-off 分析

### 5.1 高并发区对比（`--max-num-seqs=64 vs 256`）

> 注：高并发区（96/128/192）使用非流式压测，因此仅记录端到端 P50/P99 与墙钟吞吐。

| 客户端并发 | 限制 64 吞吐 | 默认 256 吞吐 | 限制 64 P99 | 默认 256 P99 | 限制 64 P50 | 默认 256 P50 |
|-----------|-------------|--------------|------------|-------------|------------|-------------|
| 16 | 800.4 | 796.2 | 10.29 | 10.31 | 9.65 | 9.62 |
| 32 | 1291.8 | 1295.7 | 12.48 | 12.65 | 11.52 | 11.46 |
| 64 | 2181.8 | 2200.1 | 14.91 | 14.88 | 14.28 | 14.06 |
| **96** | **2251.0** | **2627.4** | **26.34** | **21.93** | **18.43** | **16.17** |
| **128** | **2255.4** | **2746.5** | **28.73** | **33.43** | **26.07** | **19.24** |
| **192** | **2268.8** | **2717.6** | **48.35** | **47.37** | **39.84** | **33.52** |

### 5.2 关键拐点分析

| 区间 | 特征 | 数据佐证 |
|------|------|---------|
| **线性区（1→8）** | 吞吐近似线性增长，延迟几乎不变 | 60→226→434 t/s，P50 仅 8.1→8.8s |
| **拐点区（16→32）** | 吞吐继续涨，延迟开始明显上涨 | 800→1292 t/s，P50 9.7→11.5s |
| **饱和区（64）** | 吞吐接近天花板，延迟显著增长 | 2182 t/s，P50 14.3s |
| **过载区（96+）** | 限制 64 吞吐锁死，默认 256 继续爬升 | 限制 64 吞吐平线 ~2250，默认 256 达峰 2746 |

### 5.3 `--max-num-seqs` 的作用验证

- **安全区（≤64）**：两组几乎重合，差异 < 3%。
- **拐点（96）**：限制 64 吞吐骤停（2273→2251），P50 从 13.7s 暴涨到 18.4s；默认 256 继续涨到 2627 t/s，P50 仅 16.2s。
- **饱和区（≥128）**：限制 64 的墙钟吞吐被完全锁死在 ~2250 t/s（96/128/192 分别为 2251/2255/2268），不再随客户端并发增长。默认 256 在 128 并发时达到峰值 2746 t/s，192 时略降到 2717。

**结论**：`--max-num-seqs=64` 起到了**硬天花板**作用——服务端最多同时处理 64 个请求，多余的全部排队，GPU 已满载。默认 256 则能继续通过更大的 batch 压榨 GPU 内存带宽，直到达到物理极限。

## 六、核心机制解释

### 6.1 Continuous Batching 为何提升吞吐

**Static Batching** 的问题是：把 N 个请求打包成一个大 tensor 一起前向传播，必须等最慢的那个请求完成，整批才能释放。如果 9 个请求生成 50 token 就结束，第 10 个要生成 500 token，那 9 个已经完成的 slot 只能空转（padding），GPU 利用率暴跌。

**Continuous Batching（vLLM 用的）** 每完成一个 decode step，调度器就检查是否有请求已经完成。如果有，立刻把新的等待请求"补位"进 batch，不需要等整批结束。这样 GPU 上始终维持满负荷的活跃序列，没有空转。

**数据佐证**：并发 8 时吞吐 434 t/s，而单请求仅 60 t/s，提升约 7 倍；但端到端 P50 仅从 8.1s 涨到 8.8s，涨幅不到 10%。如果是 static batching，8 个请求串行等待，延迟会接近 8× 单请求 = 64s。continuous batching 的"动态补位"机制完美消除了这种空转。

### 6.2 PagedAttention 如何减少 KV Cache 碎片

传统实现：每个请求的 KV Cache 按**最大可能长度**预分配一块连续显存。比如 `max_tokens=512`，就预留 512 个 token 的位置。如果实际只生成了 50 token，后面 462 个位置就是**内部碎片**，无法被其他请求使用。

PagedAttention：把 KV Cache 切成固定大小的 **block**（默认 16 tokens），像操作系统的虚拟内存一样管理。请求实际需要多少 block，就分配多少，**按需增长、离散存储**。这消除了内部碎片，让显存能容纳更多并发序列。

**数据佐证**：64 并发时 GPU KV Cache usage 仅 20-30%（服务端日志），说明 7B 模型在 24GB 显存上 KV Cache 远未触顶。PagedAttention 的碎片管理让你能把并发推到 128+ 而不用担心 OOM。如果是传统连续分配，64 个请求各预分配 512 token 的 KV Cache，早就爆显存了。

## 七、最优工作点结论

### 7.1 约束条件下的最优配置

| 业务约束 | 推荐配置 | 客户端并发 | 墙钟吞吐 | P99 延迟 | 说明 |
|---------|---------|-----------|---------|---------|------|
| **P99 < 15s（延迟敏感）** | 64 或 256 均可 | **64** | **~2200 t/s** | **~14.9s** | 延迟和吞吐的最佳平衡点 |
| **P99 < 25s（中等延迟容忍）** | 默认 256 | **96** | **~2627 t/s** | **~21.9s** | 吞吐显著提升，延迟可控 |
| **吞吐最大化** | 默认 256 | **128** | **~2746 t/s** | **~33.4s** | 接近 GPU 内存带宽极限 |
| **需要过载保护** | 限制 64 | **64** | **~2200 t/s** | 超限时硬锁死 | 防止突发流量导致雪崩 |

### 7.2 瓶颈定位

- **Prefill 不是瓶颈**：TTFT 始终 < 0.1s，prompt 处理几乎瞬时完成。
- **瓶颈在 GPU 内存带宽（decode 阶段）**：TPOT 随并发线性增长（17ms → 28ms），说明每步 decode 需要加载的 KV Cache 和权重随 batch size 增加，单 token 耗时被拉长。
- **相比单请求，64 并发下吞吐提升约 36 倍**（60 t/s → 2200 t/s），这是 continuous batching 的核心收益。

## 八、面试话术要点

1. **"为什么 vLLM 比传统推理框架快？"**
   - 两点：Continuous Batching 消除空转，PagedAttention 消除 KV Cache 碎片。我的实验数据直接证明了前者——并发 8 时吞吐提升 7 倍，延迟仅涨 10%。

2. **"TTFT 和 TPOT 分别反映什么？"**
   - TTFT 反映 prefill 阶段（prompt 编码 + 首 token 生成），TPOT 反映 decode 阶段（逐 token 自回归生成）。我的数据里 TTFT 始终 < 0.1s，说明瓶颈在 decode 的内存带宽，不在 prefill 的计算。

3. **"`--max-num-seqs` 是性能优化参数吗？"**
   - 不是。我的实验显示，客户端并发低于 64 时，64 和 256 几乎没差别。它的作用是**过载保护**——当并发超过 64 时，硬截断吞吐、牺牲延迟来保护系统不崩溃。生产环境如果要做 QoS，可以用它做限流。

4. **"怎么找到最优工作点？"**
   - 画吞吐-P99 延迟的 trade-off 曲线，找到延迟约束下的"拐点"。我的实验里，P99 < 15s 时最优并发就是 64，吞吐约 2200 t/s。超过这个点，延迟会非线性暴涨。

5. **"显存拆解你会吗？"**
   - 7B FP16 权重约 14GB，KV Cache 按我的实验 64 并发下仅占 20-30%（约 4-6GB），Activation 和内存池开销约 2-3GB，总共约 21GB，和 `nvidia-smi` 观测一致。
