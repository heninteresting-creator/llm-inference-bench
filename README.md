# LLM 推理服务部署与性能压测（vLLM / RTX 4090）

在 RTX 4090 单卡与双卡（PCIe，无 NVLink）环境下，对 vLLM 推理服务做系统化压测：基线吞吐曲线、`--max-num-seqs` 作用验证、FP16 / AWQ / FP8 量化三方对比、多卡 TP/PP 扩展性对比。

- 硬件：AutoDL，RTX 4090 24GB ×1 / ×2
- 模型：Qwen2.5-7B-Instruct（基线 + 量化）；Qwen3.5-9B W4A16（多卡）
- 负载：100 条中文 prompt 五档混合（short / mid / mid_long / long / extra = 20/20/25/20/15），`max_tokens=512`
- 压测脚本：`scripts/bench_compare.py`（asyncio + aiohttp，SSE 流式采集 TTFT / TPOT）

## 结论摘要

1. **基线（7B FP16 单卡）**：单请求 60 t/s → 64 并发 2200 t/s；TTFT P50 全程 <0.1 s，瓶颈在 decode 阶段（TPOT 17→28 ms）。
2. **`--max-num-seqs` 不是性能参数，而是过载保护**：并发 ≤64 时与默认 256 差异 <3%；≥96 时吞吐锁定在 ~2250 t/s 平线，P50 随排队从 13.7 s 涨至 39.8 s。
3. **量化（64 并发）**：FP8 达 3324 t/s（较 AWQ +36%）；AWQ 单请求延迟最低（TPOT 8 ms），但 c1→c64 扩展性仅 19×，FP8 为 36×。
4. **多卡（9B W4A16，PCIe 无 NVLink）**：TP=2 效率随并发由 83%（1.67×）降至 62%（1.24×）；PP=2 全程 ≈1.00×。结论：单卡可装载的模型，应优先部署多个独立实例。

## 方法与指标定义

- **TTFT**：请求发出 → 收到第一个 content chunk（prefill 阶段）
- **TPOT**：(结束时间 − 首 token 时间) / (输出 token 数 − 1)（decode 单步均耗时）
- **墙钟吞吐**：总生成 token ÷ 整批墙钟时间
- **P50 / P99**：端到端延迟分位（最近邻取值，见「局限」）

```bash
# 复现
pip install vllm
python -m vllm.entrypoints.openai.api_server --model <model> --dtype half --max-model-len 4096
python tools/gen_prompts.py
python scripts/bench_compare.py
```

## 关键机制

1. **continuous batching**：static batching 需等最慢请求完成、slot 空转；continuous batching 每个 decode step 动态补位，权重只读一遍 → 单请求 60 t/s，64 并发 2200 t/s。
2. **吞吐口径修正**：早期脚本用「总 token ÷ Σ各请求延迟」，把并发重叠当串行——16 并发报 55 t/s，反低于单请求，与预期矛盾；改为「总 token ÷ 整批墙钟时间」后，同一批数据重算为 ~830 t/s，与正式测量（16 并发 792.5 t/s）一致。
3. **AWQ 与 FP8 的差异**：AWQ 计算前需反量化（CUDA Core），高并发时与矩阵乘争资源 → 扩展性 19×；FP8 走 Tensor Core 原生路径 → 高并发吞吐与扩展性最优（36×）；低并发下 AWQ 延迟最低（decode 每步读取字节减半）。
4. **`--max-num-seqs` 的性质**：它限制服务端同时运行的序列数。产能饱和后吞吐被锁定，多出的请求进入排队、延迟线性增长——它是过载保护 / QoS 参数，不是加速参数。

## 局限

- P99 采用最近邻取值、样本量 50–320；严格做法为插值 + 更大样本量
- 96/128/192 过载区无 TTFT/TPOT（该轮使用非流式脚本）
- 多卡批次 c=1 的 P99（25–32 s）含首请求冷启动毛刺，未剔除
- 未覆盖 NVLink 拓扑；未测量量化精度损失（本仓库聚焦性能）
